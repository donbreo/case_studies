key lands at some position, too. And the rule for which server now owns which key is super simple.
You start at the key's position, you walk clockwise, and whichever server you hit first, that's the
server that owns the key. And that's it, that's the whole idea. Keys and servers live on the same
ring. Each key goes to the next server clockwise, and that's it, done. Let's say it's server B that
dies. The only keys that need to move are the ones that were pointing to server B. Those keys walk
clockwise a bit further until they hit the next server, and let's say that's server C. So, now those
keys actually belong to server C. And here's the awesome part. Every other key in the system, all
the keys that are pointing to server A, and all the keys pointing to server C, and all the keys
pointing to server D, they don't move at all. They're completely unaffected. So, with 10 servers,
when one dies, only about 1/10 of your keys need to move. Instead of 900,000 cache misses, we just
get 100,000 cache misses. So, your database survives, your system heals itself in a few seconds, and
adding a server works the same way. The new server lands somewhere on the ring and takes over a
slice of keys from whoever was handling that area. Everyone else is unaffected. And that's the whole
point of consistent hashing. It bounds disruption. Instead of everything changing when a server
changes, only a small slice changes. But, there is a catch. If you try to use a ring exactly the way

the server is gone. Usually, there are health checks pinging each server every few seconds. And
after a few failed pings, the system declares the server dead. This usually takes somewhere between
5 and 30 seconds. Second, every client needs to learn about the new ring. Either someone pushes a
config update to all of them, or they pick it up through service discovery. And now all clients know
that the dead server is gone, and they route around it. Third, the keys that got remapped start
getting requested. They're not on the new server yet, so they become cache misses. The new server
fetches them from the database, and caches them going forward. Now, what this looks like from the
outside depends on what kind of system we're talking about. If it's a pure cache, like Memcached,
the remapped keys are just missing. They get rebuilt on the next read, and you see a little bump in
cache misses for a few seconds, and your database handles it, and life goes on. But, if it's a
database like Cassandra or DynamoDB, the data actually has to be there. You can't just rebuild from
the database, because it is a database. So, these systems do is replicate every piece of data to the
