millions of requests, but only hundreds of requests from hundreds of servers. This is called traffic

something else that Cloudflare did a little differently. The conventional wisdom at the time was

seconds it takes to connect. And the fear that everyone had —that the routing would change in the

change in the middle of a conversation, and what everyone feared was so rare that it didn't matter.

Now let's talk about what happens when the packet reaches the data center. If you walk into any
Cloudflare data center in any city where they have a presence, the server racks will look pretty
much the same. There is no separate server park for DNS. There is no separate park for firewalls or
for processing requests. Each individual server runs the entire software stack. DNS caching, TLS
termination, web firewall, bot control, DDoS protection systems—all of it. And any of these servers
can fully process a request for any of the millions of domains on the platform. But let's compare
this to the standard traditional model. In most companies, infrastructure is focused on specific
products. One cluster of servers is responsible for searching. Another cluster is for data storage.
Each of these clusters has its own forecasting, its own provisioning, and its own excess capacity.
But when one of the products suddenly becomes popular, the traditional architecture faces a problem.
The server cluster for this product is overloaded, while capacity in neighboring clusters remains
idle. But Cloudflare has no such boundaries . At Cloudflare, every server can run almost any
product. Therefore, computing power is not tied to individual services, but is distributed across
the entire equipment fleet. If the load on one product increases dramatically, it can borrow
resources from any machine in that city, because those machines are already capable of servicing it.
This fundamentally changes capacity planning. Instead of asking, “ How many servers do I need for a
CDN, how many for request handlers, how many for a WAF (web firewall)?” Instead of all this,
Cloudflare asks just one question. How much computing power does this city need? New product
launches also change because the new product is not deployed on new hardware. It deploys on the
hardware that already exists. So, as soon as the data processing software is released, it becomes
available almost immediately in every Cloudflare data center, drawing on the power of the entire
network. When traffic arrives at the data center, another system takes over control. This is a load
balancer called Unimog, built on XTP—a Linux kernel technology that we'll talk about later ; it
distributes incoming connections between all healthy servers. So, even within a single data center,
there are no dedicated workstations or separate servers just for CDN. Any healthy server can handle
almost any request, and Cloudflare has removed as many limits as possible within its server fleet.
This is one platform, one park, and one shared pool of capacity. This is what makes the architecture
so flexible, but at the same time creates a rigid requirement. If almost any server can serve almost
any client, then almost every server must have information about every client. This means it must
have all the data about their certificates, DNS records, firewall rules, redirects—everything must
be available locally, because the server handling the request cannot stop and ask another machine
for the client's configuration. It is to solve this problem that Cloudflare created a system called
Quicksilver. Every time someone clicks “ save” in the Cloudflare dashboard to change a DNS record,
firewall rule, or anything else, that change has to reach every Cloudflare server in every city on
Earth. And Cloudflare accomplishes this task in seconds. Imagine: you change the configuration in
one place, and within seconds, tens of thousands of servers around the world start working
differently because of this single parameter. To make all of this possible, Cloudflare created a
distributed configuration system called Quicksilver; It replaced the out-of-the-box Kyoto Tycoon
key-value store after Cloudflare pushed far beyond its design limitations. Quicksilver's success is
due to two unconventional design decisions . The first solution is quite radical: each server stores
the entire global data set. There is no partitioning or caching of hot keys, each machine contains
the full configuration for each Cloudflare customer, running into hundreds of gigabytes. The second
solution concerns the storage mechanism itself . Instead of building your own database from scratch,
Quicksilver uses LMDB—an in-memory B- tree mapped database optimized for ultra-fast parallel reads .
And that's exactly what Cloudflare needed. A single HTTP request can ask Quicksilver dozens of
times: which TLS certificate to use, which firewall rules to apply, which origin server to connect
to, which features are enabled for that client. Each of these requests is simply a local read from
memory, measured in microseconds. Now imagine that each of these questions required a network
request to the central configuration service, then it would take more time to retrieve the settings
than to service the client. And at the scale of Cloudflare, it simply wouldn't work . So instead of
speeding up network configurations, Cloudflare made network requests unnecessary at all . And if you
saw my video about Jira system design, it's almost the opposite architecture. Atlassian provides
each client with their own database. This means that every query starts with the same question .
Where is this client located? To address this, Jira created a system called TCS, while Cloudflare
took the opposite direction. So there are no routing issues, and almost every server already has
local configurations for all clients. So, data searches disappear completely. But now a new
challenge arises. Every configuration change must be replicated throughout the network. So
Cloudflare decided to charge a price when writing, so that reading this data would be almost free.
There's one thing you should remember from this section: it only takes a few seconds for Cloudflare
to propagate all changes to all servers around the world. And this is possible thanks to
Quicksilver. This speed, provided by Quicksilver, is Cloudflare's main advantage during DDoS
attacks. But later in the video I will show how this causes the slightest mistake to instantly
spread throughout the network. Earlier in the video, I mentioned traffic clearing centers. If you
don't work with cloud infrastructure, the name " clearing centers" may sound quite strange. But the
traditional DDoS protection industry is actually built around such centers—a small number of
specialized facilities with huge bandwidth . When an attack is detected, the victim's traffic is
redirected through such a center. There it is cleaned and sent onward. But each stage of this
purification process has its own price. Detection and redirection take minutes, and such a
workaround also adds delays to all legitimate traffic. In addition, there is another limitation.
Your protection is ultimately limited by the total capacity of these purification centers. If you
build a capacity that can absorb, say, 20 terabits per second of attack, then that will be your
limit or " ceiling." But Cloudflare took a different approach. Cloudflare has no clearing centers at
all. Each Cloudflare data center is part of a security system. If you remember what Anycast does
that I mentioned earlier: the same IP address exists in every Cloudflare location. Therefore,
Internet routing naturally directs traffic to the nearest data center. So, if it's a 30 terabit
attack, but it's being carried out from different machines around the world, then locally for each
data center in each city it will only be a small spike, not a powerful attack. Because Cloudflare
has 330 cities, even large attacks of 31.4 terabits look like tiny bursts. This means that a single
Cloudflare server is not trying to absorb the entire 31.4 terabit attack. His task is much simpler.
It identifies and intercepts the few gigabits of malicious traffic that come to that particular
server, as the traffic is distributed across cities, and even a large 31.4 terabit attack doesn't
come close to the network's capacity of over 550 terabits. The intensity of modern attacks makes
another point imperative: approximately 9 out of 10 network-level attacks last less than 10 minutes.
In fact, some of the largest attacks recorded by Cloudflare lasted much less. A few years ago, there
was a 7.3 terabit attack that delivered its entire volume in 45 seconds, and the 31.4 terabit attack
we're talking about—the record-breaking attack of 2025 —lasted just 35 seconds. Therefore, a
prerequisite is to exclude the person from this process, because they will not even have time to
approach the keyboard when the attack ends. That is why there are no people in the protection level
. The first stage is detection. Each server runs a small background program called DOS. This stands
for " denial of service daemon", it selectively inspects packets passing through the network card,
looking for statistical signs of an attack and creating a fingerprint by analyzing the
characteristics of the packets, which allows you to distinguish malicious traffic from legitimate
traffic. Once a fingerprint is generated , Cloudflare immediately sets a rule on the server that
tells it to drop every packet that matches that fingerprint. So the next time a matching packet
arrives, it is instantly discarded without spending any additional resources. There are no requests
to the central node that could add latency. Additionally, Cloudflare has a global discovery system
that monitors traffic across the network for patterns that only become visible when data from all
cities is combined. Therefore, once the system determines a reliable fingerprint, Quicksilver
distributes it to all servers within seconds. The second level is where these rules are actually
enforced. Once you have identified a malicious package, a simple question arises. How quickly can I
get rid of this malicious package? Cloudflare runs its filtering rules in XDP, which stands for "
eXpress Data Path". Let me give you a little context if you're not an expert on Linux internals. So,
Linux supports a technology called eBPF, which allows developers to load small, tested programs
directly into the kernel. These programs can run at several points in the network stack, and one of
them is XDP, the very first moment a packet enters the system. Imagine a packet arriving on a Linux
server. The packet just came from the network card. The kernel has not yet had time to allocate
memory for it. It didn't even enter the TCP/IP stack. And up to this point, almost no work has been
done. So if a packet matches a DDoS fingerprint, Cloudflare drops it right on the spot. No time is
wasted on processing it and no memory is wasted on buffering. According to Cloudflare's experience,
this is ten times cheaper than dropping the same packet later through iptables. And their philosophy
is simple. The cheapest package is not the one you process efficiently . This is one that you don't
have to handle at all . When you combine these two factors, you get a completely different kind of
DDoS protection. The system does not wait for a person to recognize an attack. It detects it,
creates a fingerprint, applies mitigations, and automatically starts dropping packets. This is why
the largest DDoS attacks in history are mitigated in milliseconds, long before a human intervenes.
And you can see it in the record books. Throughout 2025, records for the largest publicly disclosed

Okay, back to the video. Cloudflare Workers had to solve one problem: how to run untrusted code for
hundreds of thousands of different clients on every server in the network alongside systems serving
other traffic. Quick note: if you don't know what workers are, I do n't mean employees. I mean
computer programs that run asynchronously. I clarify this because sometimes juniors watch us, and
they don't always understand what I mean by "workers ." So, there are two industry standard
solutions for running untested code on machines . These are two commonly accepted approaches. The
first option is virtual machines (VMs). As you know, they have powerful protection, but they are
very heavy because they take seconds to start and consume significantly more memory per client. The
second option is containers. They are lighter, but their " cold start" still takes hundreds of
milliseconds and requires tens of megabytes of memory for each. But Cloudflare chose something
different. They chose V8 isolates. This is the same sandbox technology that Chrome uses to prevent
one compromised browser tab from affecting another. A single operating system process runs the V8
JavaScript engine , and within that process live thousands of isolates— independent JavaScript
runtimes, each with its own stack and execution context. Creating a new isolate takes only a few
milliseconds and consumes only a few megabytes of memory. According to Cloudflare's published data,
this system actually runs 100 times faster than a container, consuming only a tenth of its memory.
And the reason Cloudflare cares so much about lightweight isolates is for placement density . If
each worker consumed hundreds of megabytes like a virtual machine, only a few of them could be
hosted on each server. And while consuming several megabytes, each server can simultaneously hold a
huge number of workers in memory. And this fundamentally changes the deployment process. Publishing
a worker does not mean choosing the region where it should run. The worker is simply sent to the
entire server park . And almost every Cloudflare server is capable of running it. And if you think
about it, this is the same architectural idea that we've seen throughout this video: now almost any
server can run the code of almost any client. And that's not all. They also solved one of the
biggest problems with serverless platforms—cold starts. And this solution only works for Cloudflare
, because Cloudflare is located right at the edge of the internet. So when your browser opens a TLS
connection, the first message, called "client hello" , already contains the name of the host it is
addressing, in a field called SNI. And this happens before the TLS handshake is even complete and
before the HTTP request appears. But this is enough for Cloudflare to understand which worker will
ultimately handle this particular request. Therefore, instead of waiting for the HTTP request to
arrive, Cloudflare starts loading the worker isolate during the handshake itself . The network still
takes a few milliseconds to complete TLS. So the isolate only needs a few milliseconds to run. So,
these two things can happen in parallel, and by the time the first HTTP request arrives, the worker
is ready to go. So cold start hasn't disappeared . Cloudflare simply hid it inside the latency that
the connection is still paying for. Now, running thousands of clients within a single process
naturally raises an interesting question: what prevents one client's code from reading the memory of
another? And Cloudflare took a really strange approach to answering this question. They removed the
concept of time inside the worker process. I know this sounds silly, but let's talk about it in the
next section. For years, Cloudflare's architecture worked quite well, but then a vulnerability
emerged that shattered one of the fundamental assumptions of the internet. In 2018, Spectre
happened. So, Spectre was not a bug in JavaScript. This was a vulnerability in modern processors.
Modern processors use a method called speculative execution, where they try to predict what your
program will do next and start executing those instructions without knowing if they will be needed.
So, if the prediction turns out to be wrong, the processor discards those calculations, but does not
erase all the side effects. Some of these side effects remain in the processor cache. Inspector
showed that even rejected assumptions can leave traces in the cache, and attackers can use these
traces to gain access to data they were not supposed to see. And the way attackers do this is very
inventive. They carefully measure tiny discrepancies in time, and this can reveal data they
shouldn't have access to. If you don't know how these attacks work, how Spectre works, how these
timing discrepancies and speculative execution work—it's okay . You don't have to be a security
engineer to know all this. But since I have a background in offensive safety, I'll try to explain it
to you in a few words. This means that accessing data that is already in the processor cache is much
faster than reading it from RAM. By measuring these tiny differences in time, an attacker can figure
out which pieces of data the processor has secretly touched during speculative execution. This is a
hardware problem and cannot be completely fixed through software. In other words, Spectre turns time
into a channel for information leakage. The rest of the software industry had a common answer to
this: separate processes and virtual machines for each client. But Cloudflare can't rely on this
because, as you remember from the previous section , Cloudflare Workers are built on isolates, and
thousands of them knowingly use the same operating system process. So Cloudflare had to approach the
problem from a different angle. As Kenton Ward, the architect of Workers, points out, every Spectre
attack is fundamentally a time attack, and every time attack requires a clock. So Cloudflare just
took that watch away. Now, inside the worker, time does not pass while your code is executing . So,
if you call it twice in a tight loop, you'll get the same result, no matter how much work was done
in between. The clock only moves forward when your code performs input/output (IO ) operations. You
cannot measure your own execution time. But attackers quickly found another way to create a highly
accurate clock. Instead of relying on the system clock, they ran a second thread whose sole task was
to increment a shared counter as fast as the processor would allow. Reading this meter actually gave
them an accurate timer. But Cloudflare Workers closed this loophole as well. There are no streams
there. There is no shared memory or shared array buffer inside the sandbox. So there's nowhere to
create this counter. Therefore, the attackers further improved their attack. They started contacting
a remote server to ask for the time. But using a remote server as a clock doesn't help with
Cloudflare, as network latencies are measured in tens of milliseconds , completely negating the
nanosecond time discrepancies required by Spectre. It's worth knowing that all of Cloudflare's
measures to prevent Spectre attacks do not make Spectre theoretically impossible. This only makes
data mining so slow that it ceases to be an attack. And Cloudflare has added another precaution. If
a worker starts behaving as if it is carrying out a Spectre attack, Cloudflare moves it into its own
operating system process, providing complete isolation with no changes to other processes. So
imagine it like this. Everyone shares a common room until someone starts acting suspiciously , and
then you start isolating that person. And finally, there is another layer of protection that
Cloudflare uses. Workers actually run on Google's V8 engine. This means that V8 security fixes
become Cloudflare security fixes. So when a new version of V8 is released, Cloudflare re-builds it
and deploys it across the entire infrastructure within a few hours. Cloudflare Workers is a brand
new runtime environment designed with these lessons in mind. But one critical part of the request
pipeline was still written in C, and every request went through it, which remained Cloudflare's
biggest security risk for years. In 2017, this risk finally became a reality. In February 2017,
Travis Orandi from Google Project Zero contacted Cloudflare with some very bad news. He discovered
that a bug in Cloudflare's front-end software could, under certain conditions, cause server memory
fragments to leak in HTTP responses. That in itself would be very serious. But in Cloudflare's
architecture, it was much worse. If you remember what we discussed throughout this video: a single
process handles traffic from many different clients. So the memory that was next to one client's
request did not necessarily belong to that client. It could contain cookies from another client with
data like authentication tokens, parts of POST requests, and fragments of completely unrelated
traffic. This bug was contained in the HTML parser, written in C. It was used by functions that
rewrote pages "on the fly". And on certain malformed pages, this parser read data outside its
allocated buffer. This means that instead of stopping where it should, it went into whatever was
further in memory and returned those parts in HTTP responses. And the craziest thing is that some of
these responses were even cached by search engines , making the stolen data publicly available to
everyone. This vulnerability became known as Cloudbleed, it's a very, very well-known vulnerability,
and it's a real nightmare for the sharing architecture that Cloudflare has. So what happens here is
that the memory error is not limited to a single client process. It can expose the data of all other
users as well. And Cloudbleed changed the direction of Cloudflare's engineering forever. So
everywhere Cloudflare was writing code for new ways to handle requests. They translated it into the
Rust programming language, and the most important example of this was a solution called Pingora.
This is Cloudflare's replacement for Nginx on the origin-facing side. They started using it in
production in 2022 and opened the source code in 2024. Nginx now runs multiple independent worker
processes, each of which maintains its own persistent connections to the origin server. The trick is
that all these pools are completely isolated from each other. So, if worker process A has an active
authenticated connection to your server, process B cannot use it. So, worker process B has to open a
completely new TCP connection and perform its own TLS handshake. At Cloudflare's scale, this means
millions of unnecessary connections and handshakes every day, even if another process on the same
machine already has a free connection ready to use. Pingora removes this limit, and instead of many
independent worker processes, it is now a single multi-threaded process with a shared connection
pool. And each thread here can reuse the same active connections to the source servers. And that
means significantly fewer new TCP connections, fewer TLS handshakes, and less work for both
Cloudflare and the origin servers behind it. Cloudflare's published metrics are impressive. Pingora
now processes over 8 trillion requests per day, using approximately 70% less CPU time and 2/3 less
RAM than the Nginx-based service it replaced. So, as we just established, the bug was contained in
the legacy Cloudflare proxy server, which was a large C codebase that handled every request that
passed through the network. And after Cloudbleed, Cloudflare began rewriting the business logic of
this proxy in the Rust programming language. Historically, this logic existed in the form of Lua
scripts built into Nginx. It was rewritten in Rust as a new engine, which they called FL2. Together,
Pingora and FL2 modernized the software that handled every request that passed through Cloudflare's
edge. But even perfect software has its limits. And when a request leaves Cloudflare and goes to
your origin server, it still has to travel across the internet. And this path, as you know, is
usually determined by the BGP protocol. But Cloudflare decided that this wasn't enough for them .
Now, we spent most of this video inside the Cloudflare network. Now let's look at what happens after
the request leaves the Cloudflare network. By default, Cloudflare does not choose how exactly this
request will reach your regional server. The Internet does this using a protocol called BGP. BGP is
a protocol that tells networks how to communicate with each other. But BGP was not designed to find
the fastest path. It was created to find an accessible path. It makes routing decisions based on
network policies and the sequence of networks a packet traverses, not based on performance. He
doesn't know about delays and doesn't see congestion. A route that seems good for BGP can easily
turn out to be slower than another one available at the same time. So the path your packets take
over the internet is often not the fastest. And most companies simply have to accept the fact that
they do not control Internet routing. They get the path that BGP chooses. Cloudflare, however, is in
a completely different situation. Its network spans hundreds of cities, and billions of requests
pass through Cloudflare every second, giving the company something very few have—a real- time view
of how the internet works. So she has the data to answer the question: How long does it actually
take to get from this city to that server right now? Which roads are congested? Which of them
suddenly became faster? Cloudflare can continuously measure these metrics. Argo is a system that
Cloudflare created to take advantage of this information. Instead of blindly following the path that
BGP would take, Argo looks at Cloudflare's current measurements and asks a different question. Which
way is the fastest now? Sometimes the answer is obvious. And sometimes—no. And instead of sending
the request directly from the inbound data center to the client’s server, Argo can first route it
through Cloudflare’s own private network to another location before sending it to the target. Thus,
Cloudflare's own data centers become transit points. And this leads to one of the most striking
ideas of this architecture. Sometimes the fastest way from A to B is through C. It sounds a bit
illogical, but think about your navigator. Sometimes he intentionally drives off the highway because
traffic jams make the shortest route the slowest. And in Internet routing, the same problem. The
direct path is not always the fastest. The difference is that Argo doesn't guess. She actually
measures. And Cloudflare describes Argo as a virtual backbone for the internet. The network now
constantly monitors real-world traffic, learning which paths work best and routing future requests
accordingly . When Argo was launched , Cloudflare reported that for approximately 50,000 beta
customers, average latency dropped by 35% and the number of connection timeouts decreased by 27%.
One customer, OKCID, saw a 36% reduction in query latency without changing a single line of
application code. Now it is worth paying attention to another pattern. Argo exists because
Cloudflare already had something that almost no one else had —a global view of internet performance.
And they turned that visibility into a product. We've seen this same idea several times in this
video. Anycast turns internet routing into a load balancer. The free tier turns millions of small
sites into an attack detection network. And Argo here converts billions of requests into a live
traffic map. So, time and again, Cloudflare takes the information that is a byproduct of working at
scale and builds new capabilities on it. So, Argo solves one problem here: finding a faster path to
the source server. Back in 2014, Cloudflare wanted to serve banks and other highly regulated
organizations. There was only one problem. To complete a TLS connection, Cloudflare typically
requires the website's private key. And this is obviously how TLS works. The private key verifies
the identity of the server, and whoever holds it can impersonate the website. For most customers,
transferring this key to Cloudflare was not a problem. But for the bank, it was an absolute problem.
So, the TLS private key is one of the most protected secrets in the bank. And in many regulated
industries , especially financial ones like banks, policy simply doesn't allow the key to leave the
customer's infrastructure. And for many years, this meant that such customers, who were heavily
regulated, could not use Cloudflare. But the breakthrough came when they looked at the TLS handshake
itself. It turns out that the private key is only needed once—right at the beginning of the
handshake. So, there is only one cryptographic operation that requires it. After that, the rest of
the handshake and all encrypted traffic that follows no longer require the private key. So
Cloudflare asked a simple question. What if this single operation had taken place elsewhere? And
that's exactly what Keyless SSL does. Now the private key never leaves the client's infrastructure.
It often remains inside a specialized hardware security module, or HSM. And Cloudflare performs
almost all TLS handshakes at the network edge. Then, only at the moment a private key operation is
required, it sends just that cryptographic request to the client's key server, which performs the
operation, returns a signed result, and Cloudflare completes the handshake. So, the private key
never leaves the client's control, but Cloudflare still terminates the TLS connection. In my
opinion, this is an extremely good idea, since the TLS handshake is shared between two different
machines. Everything happens on the periphery, and cryptographic operations are performed in the
HSM. Cloudflare does almost everything, and the client performs only the one operation that requires
the secret key. Of course, such a division has its compromises. Each new TLS connection now includes
an additional network request to the client key service. This typically adds a few tens to a few
hundred milliseconds, depending on the location of the key server. But fortunately, we pay this
price mostly only once, at the beginning. Once a TLS session is established, the private key is no
longer needed to re-establish it. So regular visitors usually don't encounter this additional
request at all. But there is another problem. The key server now becomes part of the critical path.
If it is unavailable, new TLS handshakes cannot be completed . So Cloudflare made it stateless,
allowing customers to run multiple key servers behind a load balancer. Because these servers perform
cryptographic operations on behalf of the client, the communication between Cloudflare and the key
server is protected by mutual TLS. Cloudflare even made both sides of the protocol open . But
there's another reason why this is interesting. This completely destroys the architectural pattern
we observed throughout the video. Time and again, Cloudflare pushed data out. There were client
settings, certificates, firewall rules—everything was copied across the entire server park so that
the periphery never asked other machines for anything. But Keyless SSL does the exact opposite. It
pays the cost of the network request for each new handshake so that the private key never leaves the
client's control. And that means that sometimes copying data everywhere is the right decision. But
sometimes the right solution is to have only one copy. Cloudflare liked this pattern so much that
they later implemented it internally . So even when clients trust Cloudflare with their private key,
the edge process handling the TLS connection no longer has direct access to it . This idea— a single
authorized owner for the most sensitive state— has proven to be extremely effective in other areas
as well. But later, Cloudflare encountered a different type of problem. This time the task was not
to protect classified data. It was about managing data that was constantly changing, and that data
needed only one authoritative place to be stored. So let's talk about that in the next section. Up
until this point, almost everything we've looked at has followed the same pattern. Copy data
everywhere, support stateless services, or cache responses. And this works quite well for
configurations, certificates, and content that is mostly read-only. But some tasks simply don't fit
into this model. For example, a chat room, a game lobby, or a collaborative document. All of these
things have something in common. Multiple people are trying to update the same state at the same
time. Cloudflare already had a global storage system called Workers KV. But Workers KV is designed
for a different job. It replicates data globally and provides eventual consistency, which is great
for read-intensive tasks. But it's a poor tool when two people in different parts of the world try
to increment the same counter at the same time. So Cloudflare's response was to deliberately violate
one of the main rules we talked about: instead of putting data everywhere, they put it in one
specific place, and this is called durable storage. This is what a durable object is. A durable
object is a piece of code with its own private storage. And at any given moment in time, there is
exactly one instance of this object in the world. So regardless of where the requests come from,
every request for that object's ID is directed to the same instance. And these requests are executed
one after another. This solution simplifies almost everything. There is no need for consensus
protocols, quorums, or conflict resolution because there is only one copy of the state . So, there
is nothing that needs to be agreed upon. If two users send messages to the same chat at exactly the
same time, both requests go to the same durable object. One of them is processed first, and then the
other. Order arises naturally because there is only one place for a change of state . If this sounds
familiar, it should be, as it is essentially the actor model popularized by the Erlang language,
ported to JavaScript. And I think that's the most important architectural lesson in this chapter, at
least. Cloudflare has been distributing data like configurations, certificates, firewall rules for
years, all of which is replicated across their entire network. Instead, durable objects deliberately
override this decision, and they found that replication is ideal for stateless services and data
that is mostly read . But some problems cannot be solved by creating more copies. So when thousands
of users are updating the same amount of data, there must be one authoritative source of truth. OK.
