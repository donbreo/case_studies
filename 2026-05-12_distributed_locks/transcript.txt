require a majority to agree. The idea was that distributing the lock across multiple Redis nodes

help if your client itself goes silent for 12 seconds. So, if more Redis instances aren't the
answer, what is? Kleppmann's answer is called fencing tokens. And once you see it, it changes how

server hands out a number, which is a fencing token. Process A gets token 33. Later, when process B
acquires the lock, it gets token 34. The numbers only ever go up. Now, here's the awesome part. When
process A goes to write to the database, it includes its token number 33 in the write. The database
checks, is this token greater than or equal to the highest token I've seen so far? If yes, it
accepts the write. If no, it rejects it. So, let's replay our scenario. Process A grabs the lock,
gets token 33, starts working, and process A, just like the last time, pauses for 12 seconds. And
until then, the lock expires. Process B grabs the lock, gets token 34, and makes its write. The
database sees token 34, accepts it, and remembers 34 as the highest. Then, process A wakes up, tries
to write with token number 33. The database sees that 33 is actually lesser than 34 and rejects the
write. And this is how we just prevented damage. So, the lock can fail and two processes can both

the database is. The lock is just a performance optimization on top. And the lock is there to make

a heartbeat. The holder periodically renews it, say every 5 seconds for a 15-second lease. If the
renewal fails because the process paused or the network went down, the lease expires and someone
else can acquire it. Now, the rule of thumb here is set your lease TTL to about three to five times
the expected work duration and renew at TTL divided by three. That gives you two missed renewals
before the lease expires, which absorbs brief network blips without falsely declaring the holder as
dead. Leases don't solve the pause problem on their own. If your process pauses, your renewal thread
pauses, too. When you wake up, the lease may have already expired and someone else may have it. So,
leases give you liveness, but you still need fencing tokens, as we saw earlier, for safety. Lease

need a lock that's safe by itself without having to add fencing tokens to every storage system, you
need consensus and the standard tools for that are Zookeeper and etcd. Zookeeper has a clever
pattern for locks using something called ephemeral sequential nodes. When a process wants the lock,
it creates a node and gets a sequence number. The lowest number wins and each waiter watches only
the node right before it in line. So, when someone releases, only one waiter gets notified, so
there's no thundering herd. And the nice part is that the nodes are ephemeral, which means they're
tied to the client's session. If the holder crashes or loses its connection, Zookeeper detects it,
deletes the node, and the next waiter automatically takes over. So, no timeouts and no fencing
tokens needed. The trade-off is latency. Zookeeper operations are 5 to 15 milliseconds compared to
