takes is fully reversible. So, every checkpoint, every change, all the way back to the start of the
session. But, to pull that off, you have to think about state in three layers because the agent
touches three different kinds of state, and they don't behave the same way. The first layer is the
file system. This is where the code lives. So, files that the agent creates, files that it edits,
files that it deletes. And the way Replit handles this is with copy-on-write underneath the file
system. And the way copy-on-write works is that when you take a snapshot of a file system, you don't
actually copy any data. You just record a marker that says, "This is where the file system was at
this moment." So, future writes don't modify the original blocks. They write new blocks, and the new
blocks become part of the live file system. And the original blocks stay around untouched, available
to roll back to. Now, the beautiful part of copy-on-write is that the snapshot itself is constant
time. So, it doesn't matter if your project is 1 MB or 1 GB, taking the snapshot is just writing a
marker. And it just takes milliseconds. So, Replit can snapshot the agent's file system at every
single step of its work without slowing anything down. And rolling back is just pointing the file
system at an earlier marker. The second layer is the code itself. This sits on top of the file
system, but it's a separate concern because the way you think about code changes, like diffs,
commits, and branches, is different from how you think about file system state. Replit handles this
with Git, but the way they use Git is interesting. Every meaningful action the agent makes
automatically creates a Git commit in the background. So, even if the user never touches Git
themselves, they're getting a complete commit history of everything the agent has done. And there is
an immutable backup remote. So, even a full file system deletion does not lose the history. This
means users can scroll back through the agent's work the same way that you scroll back to your own
commits and revert to any point. So, for beginner users, it's just a single button that says, "Go
back to before that broke." But for power users, it's a full Git panel where they can branch, merge,
and cherry-pick. Now, after this, the third layer is the database, and this is where it gets
generally hard because file systems and Git are both easy to snapshot. They're just bytes, but
databases are different. A database has live connections, in-flight transactions, and internal
write-ahead log. So, you can't just copy-on-write your way around a running Postgres. The way Replit
handles this is something they call forkable Postgres. The development database, which is the one
that the agent is using while it builds, is architected to support forking. So, when you take a
