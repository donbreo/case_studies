Let's first look at the obvious answers and consider why they don't hold up. The first thing most
engineers turn to is the container. You've probably used Docker. A container packages an application
so it runs in its own isolated bubble, with its own files, its own processes, its own view of the
world. From the inside, it looks as if the program has the entire machine at its disposal . But
there is one trick, and it is important. All of these containers on a machine have one thing in
common –the operating system kernel. And the kernel is the core of the operating system, the part
that actually manages the hardware, i.e. the disk, memory, network card, and processor. Your program
can't directly touch any of this, and every time the program wants to do something real, like open a
file, send a network packet, and request more memory, it has to ask the kernel to do it. The program
is effectively locked in a room. The only way it can affect the outside world is to slip a request
note under the door to the kernel, which reads the note and decides whether to act on it or not.
These requests have a name , and they are called system calls, or system calls for short . Remember
this word, because it will be remembered much later. Now here's why containers are not enough for
untrusted code. Every container on the machine pushes records under the same door to the same
kernel, and that kernel is one common guard for everyone on the machine. So if malware finds one bug
in the kernel, one flaw in the way it reads a particular node, it can trick the guard, break out of
its room, and suddenly it's no longer isolated. She stands in a hallway with access to the entire
building, every other container, everyone's data. This is called container egress, and for untrusted
code, it's not hypothetical, it's actually a common class of attack. So containers are good for your
own code, code you trust, but for outsiders, one common core is that it's too thin a wall. So the
next natural thought is: don't share the kernel, give each user their own full virtual machine. A
virtual machine is an entire simulated computer running on top of a real one, with its own full-
fledged operating system and its own kernel inside. Now there is no shared protection, each user
gets their own building, their own security, completely separate from everyone else. This is the
gold standard of insulation. Now, to break out, an attacker would have to escape the entire
operating system, and then the hardware-imitation layer underneath it. But virtual machines are
heavy, each one has to load a full operating system, and each one reserves a large chunk of memory
and CPU just to exist before doing any of your actual work, and deploying one of them takes real
time. Now imagine doing this for millions of people, most of whom open a laptop, run a few cells for
10 minutes, and leave. You would have to constantly download and disassemble full operating systems
and back up mountains of hardware that is mostly idle . At the scale of Colab, and at the price of
free, this math simply doesn't work. So, that's the problem. Containers are cheap, but too weak for
unreliable code. Full-fledged virtual machines are powerful, but too expensive to give away for free
at this scale. What Colab needs is what isn't on this menu. Virtual machine level isolation at the
price of a container level. And that's exactly what Google created. The answer is a technology
called gVisor. Google created it specifically for this problem, safely running untrusted code, and
Google runs every session inside it. It's an open source program, the code is right in front of you,
you can read it, and the basic idea is quite simple once you understand it. Remember the container
problem? Untrusted code passes its system call notes directly to the one real kernel, and one bug in
that kernel means everything is at stake. So what if the untrusted code didn't communicate with the
real kernel at all? What if you put a second core between them, a substitute that catches each note
first? That's what gVisor is. This is what is called the kernel of the program, and it runs like a
regular program in regular user space, not in a real operating system. And the part that does this
job is called a sentry. Sentry itself is a core. It reimagines much of Linux's behavior, but is
written in Go, a memory-safe language chosen precisely because entire categories of classic security
bugs are much harder to write in it. So now the unreliable code is locked in its room, slipping
notes under the door, only on the other side of the door is no longer the real core. This is the
sentinel, the second core that stands in the way. So, here's what exactly happens when your code
makes a system call. Typically, a program makes a system call, it goes directly to the host kernel,
and the host kernel executes it. One jump, and a direct connection to the most powerful, most
sensitive parts of the software on the machine. But with gVisor, things are different. The program
makes a system call, and gVisor intercepts it before it reaches the real kernel. It passes the call
to the watchdog, and the watchdog handles it itself in user space , emulating what a real kernel
would do. Untrusted code thinks it is communicating with Linux, but it is not. He simply
communicates with a careful re-implementation that watches every step. And here is the key
consequence. The actual host kernel, the de facto guardian of the entire machine, hears almost no
untrusted code. Almost everything is absorbed and processed by the sentinel. The real kernel sees
only a small, fixed, carefully vetted set of ins- requests coming from gVisor itself, not the broad
stream of system calls generated by user code. So you've taken the huge attack surface of anything a
program can ask the kernel for and reduced it to one narrow control channel. Now a quick note for
those wondering how it actually intercepts calls: gVisor does this either through a Linux feature
called seccomp, which allows it to intercept system calls, or through hardware virtualization. In
any case, the essence is the same . Nothing that the user code requests reaches the real kernel
directly. All of this is intercepted at the door. Now let's talk about why this provides isolation
that is close to a full virtual machine, but at a much lower cost. Think about what the attacker
would have to do now to actually break out and get to the host machine. First, they need to find and
exploit a bug in sentry, the gVisor core. Let's assume they succeeded. Now they are inside gVisor,
but gVisor itself is a locked down unprivileged program. It doesn't just protect the host from code.
It also isolates the host using the same Linux isolation features and drops almost all of its own
privileges before any of your code even starts executing. So, after cracking sentry, the attacker
still has to separately find and exploit a bug in the real host kernel. And here's the key part.
These two kernels, sentry and host kernel, have no common code at all. They are completely
independent implementations. So, a mistake in one is not a mistake in the other. You are not asking
an attacker to break one lock. You're asking him to pick two completely different locks one after
the other, where the key to one tells you nothing about the other. This is a much higher bar than a
single shared core of a simple container. So, here is a clean version of the entire security system.
Untrusted code never touches the real kernel. He touches the second core that stands in his way, and
breaking it means defeating two unrelated cores in a row. Now, all this interception is not free.
Recycling every system call has overhead, and it's interesting what that overhead goes towards. They
are almost entirely spent on the heavy lifting of system calls, things that constantly overload the
disk or network, such as databases or load balancers. For them, gVisor can cost you a significant
performance loss, on the order of 10-30%. But look at what Colab users actually do. They train
neural networks, multiply huge matrices, and run number processing cycles on a GPU . Such work is
limited by computing resources. Once it starts, it spends almost all of its time performing raw
mathematical calculations on the processor and interacts almost completely with the operating system
. It makes very few system calls in its hot loop. So the only thing Gvisor attacks is system calls,
which the Colab workload barely does, meaning that the sandbox , which would be painfully slow for
the database, is almost free for machine learning. And besides, the work on the GPU is performed
directly on the real accelerator at full speed. The sandbox is around the code, not in the middle of
number processing. This is a case where what the workload actually does is much more important than
any benchmark. The same tool is a bad choice for one type of system and perfect for another. Colab
just has exactly the kind of workload where heavy isolation costs next to nothing. They get virtual
