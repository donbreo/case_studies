the scheduling problems by implementing the "sparest fragment first" algorithm we've seen. And they
solved the incentive issue with the "you give me, I give you" strategy and the optimistic unlocking
that we just looked at. But there is something that still remains unresolved: detection. While we've
covered all of these issues, there's one more part we need to talk about—the tracker. As of 2005,
each swarm on the BitTorrent network still depended on its own tracker. So there was a central
tracker, and its job was trivial: it just kept a list of peers, right? How many servers and which
servers are present in the network. But when it's not working, if that tracker fails, new peers
can't join and existing swarms can't be found. So this central server is not only a single point of
failure from a technical point of view, but also from a legal point of view, since it has an
operator, an IP address, and a hosting account, which is why trackers are often shut down by the
authorities. The BitTorrent network faced an engineering challenge : to decentralize the search for
participants so that it did not depend on a central tracker server. In 2005, BitTorrent solved this
problem with the so-called mainline DHT. DHT is a distributed hash table built on a 2000 protocol
called Kademlia. Let's try to figure out how it works. You already know what a hash table is. You
just give it the key and it stores the value. A distributed hash table works the same way, only the
table is distributed across millions of independent computers, rather than stored on a single
server. In BitTorrent, the key is the torrent's info-hash —another name for the SHA-1 hash of the
torrent's metadata—and the value is a list of participants distributing that file. And here we face
a real system design problem . If the table is distributed across millions of machines, which one
should store the keys? Since there is no central coordinator, Kademlia solves this with two ideas.
First: each node, when connected to the network, chooses a random 160-bit identifier. Second: each
torrent already has a 160-bit identifier—the SHA-1 hash of its metadata, known as the info-hash we
already talked about. This means that nodes and torrents use the same numbering scheme, which leads
directly to Kademlia's storage rules. The nodes whose IDs are closest to the torrent's info-hash are
responsible for maintaining the list of participants for that particular torrent . So far we've
talked about complete decentralization, but there's one centralized artifact left—the torrent file
itself. It is hosted on various sites from where we download it, but an extension to the protocol
called "metadata exchange" has helped eliminate this. As you remember, a torrent file contains
metadata. Now, thanks to metadata sharing, users can transfer not only parts of files to each other,
but also metadata. The loader checks them against the info- hash just like any other part of the
file. So, the minimum requirement to join the giveaway is just an info- hash, which is a
40-character string. Now you don't need a torrent file. If you have this info hash, you can start
loading data immediately. This info-hash is usually available in the form of a link, called a magnet
link. And I'm sure you've already seen this magnet link in many places if you've downloaded a
torrent file. So, this magnetic file can later be used to create a torrent file. Therefore, you
don't necessarily have to share a file with a .torrent extension that contains metadata. So, all the
metadata fragments that can be downloaded using this magic link can later be used to create a
torrent file. So you don't need a torrent file to join the swarm. You can simply get started with a
magic link that helps you download the metadata needed to create the file later. So, you have
essentially decentralized the torrent file itself. It no longer needs to be hosted on the website,
because even if this file is deleted, you can still do everything with just the magic link. And
that's what makes the BitTorrent network so powerful. Now let's look at the full timeline of
development. In 2001, all you needed was a website, a file with the .torrent extension, and a
tracker. In 2005, DHT replaced the tracker, and then metadata sharing replaced the .torrent file.
And finally, now you just have a magic link with a 40- character hash. The transition from this to
this, and from this to this seems insignificant. But in fact, the underlying architecture has
completely changed. A regular URL points to a location that is usually tied to a server, and servers
can go down all the time ; A magnet link points to the content, not the server address. It points to
data, and that's why any other node in the network that has that data can provide it to the
requesting node. That's how you finally got rid of the last centralized element, which was the file.
And that's why an AI lab can now release a model by simply publishing a 40-character string; the
identifier is enough and the network decides the rest. And that's why it's called a magic link,
because it really works like magic. There was another big problem in the early stages of
BitTorrent's development that actually affects the systems we still use today. Let's see how it
worked and how they solved it. So the problem was how BitTorrent traffic coexisted with other
traffic within the same connection. This means that, let's say, you run a torrent client on your
computer, and it will eventually degrade everything else on your network, like video calls, gaming,
browsing—all of which will suffer if you plan to use BitTorrent on your network. The reason is not
that BitTorrent consumes more net bandwidth . This was a phenomenon called "buffer bloat" . To
understand why this happens, we need to look at how TCP allocates bandwidth. TCP does not know what
the capacity of the network channel is. Therefore, he determines it experimentally. It continues to
transmit faster and faster until the network starts dropping packets, and only when packet loss
starts does TCP realize it has gone too far. But the problem is that home routers don't drop packets
immediately. First, they buffer the packets. So before TCP sees packet loss, these buffers are
filled completely. And every packet, whether it's a BitTorrent transfer, a video call, a game, or a
web page, eventually queues up. A torrent client usually supports dozens of TCP connections
simultaneously, and this is due to the peculiarities of the protocol's operation. It simultaneously
downloads data and distributes it to other users. Therefore, together they constantly keep the
router's buffers full. The channel has not exhausted its bandwidth. It is actually overloaded with
packets waiting in the queue, and this queue delay can grow to seconds. So the BitTorrent solution,
introduced around 2009, was to stop waiting for packet loss altogether, and instead a new transport
protocol called UTP started measuring queue latency. Packets contain timestamps, and once the one-
way delay exceeds approximately 100 milliseconds, the sender reduces the speed before the router
buffers fill up and interactive traffic is affected . And there is another clever property of UTP.
Since TCP is still more aggressive, it naturally wins when the channel becomes busy. And that's
exactly what UTP was designed for. It behaves like a background task. It only uses free bandwidth
when it is available and immediately yields to TCP when higher priority traffic that TCP is serving
appears. And this idea turned out to be quite influential. It was standardized by the IETF for the
rest of the industry under the name Leadbat. Today, the same congestion control algorithm is used
for background transfers such as Windows Updates and Apple Software Updates. And the congestion
control mechanism developed for BitTorrent is now built into major operating systems like Mac and
Windows. This architecture is actually used in many other places. In 2010, Twitter used BitTorrent
internally to deploy updates . They were able to reduce deployment time from 40 minutes to just 12
seconds by having each server reserve chunks as they were loaded. Facebook used the same idea to
send large binary files to tens of thousands of machines, prioritizing nodes in the same rack to
localize traffic. Blizzard created a BitTorrent- based patcher for World of Warcraft because patch
release day is a perfect example of the " crowd effect," where millions of players download the same
files at the same time. So, Kraken from Uber in 2018. By the way, if you don't know how Uber
actually works, I'm also planning to make a video about Uber's system design . So, Uber began
distributing Docker images across clusters of thousands of hosts using peer-to-peer (P2P)
replication. Microsoft's Delivery Optimization uses the same principle to push Windows updates to
over a billion devices. And today, this pattern has become relevant again for AI. The models weigh
tens or even hundreds of gigabytes, and the peak demand occurs in the first few hours after release.
So Mistral, a very popular company with open source models, distributes them via magnet links,
allowing the community to share bandwidth instead of centralized payment. Even a great technology
like BitTorrent has its tradeoffs, and that's the sad side of engineering: no matter how cool a
technology is, it will always have some flaws. So, the first compromise is the lack of privacy.
Membership in the swarm is public: to upload data, a node must declare itself, and any participant
can join and record every IP address they see. The same openness that search provides now makes the
list of participants visible. The second is the priority of bandwidth over latency. We've already
looked at the "rarest segment first" policy, right? As you know, " sparest first" is the opposite of
sequential loading. Therefore, the protocol is poorly suited for streaming, because the segment that
the viewer needs next is rarely the one that the swarm will replicate, as each client is optimized
to find the rarest fragment, rather than loading it sequentially. Third, availability depends on
demand. The “ crowd effect” is a strong scenario, but once demand drops, availability depends
entirely on whether nodes decide to continue distributing . And fourth, open membership has a
downside. DHT accepts any node, but that node could be an attacker who runs thousands of fake IDs to
skew search results or poison records, which is called Sybil attacks. Sybil attacks are the most
common type of attack on decentralized networks. If you don't know how they work, you can watch any
YouTube video on the topic. There are hundreds of videos about Sybil attacks. So, there are five
takeaways you can take from this video for your own systems. So, the first thing is to make demand
determine supply. The BitTorrent protocol ensures that you start sharing as soon as a new node joins
the network and receives its first fragment. The second principle to learn is that incentives are
part of the BitTorrent architecture. BitTorrent has implemented throttling and optimistic
unthrottling mechanisms to encourage users to continue sharing . The third point, which I find most
interesting, is that they were checking the content, not the channel or the node. Instead of
authenticating the node or participant entering the network, they decided to verify the content
itself. When data can verify itself, as BitTorrent does with hashes, you can use any path to deliver
it, such as untrusted mirrors, caches, or nodes. The fourth point is optimization of the entire
system, not just a single node. The BitTorrent protocol ensures that nodes download "recipes" first,
which ensures the health of the entire network . Eventually, as we discussed, both goals begin to
converge. The health of the swarm becomes the health of the node itself, because the node wants to
be able to download all the shards quickly, right? The fifth point relates to LEDBAT and UDP, which
we saw: don't make every workload compete on equal terms. Background tasks can be configured to only
use leftover bandwidth, as UDP does, instead of competing with important traffic, such as video
calls handled over TCP . This is exactly what we saw in the case of LEDBAT and UDP. The main idea
behind BitTorrent is that every downloader is also a sender, and the BitTorrent protocol does a lot
to ensure that these pieces are available. Therefore, a node can make its contribution within
seconds of joining. Peerie hashes make it safe to exchange with untrusted nodes , and the "
sparseest first " strategy ensures that every fragment is copied. Tit-for-tat contributes to the
common cause with a rational strategy. A distributed hash table eliminates centralization, and UDP
allows the entire system to coexist with the rest of the network traffic. If you saw my video about
