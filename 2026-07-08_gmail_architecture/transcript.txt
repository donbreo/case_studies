Gmail. The first version of Gmail was built by a single engineer in a single day, pointing the

The second is a new private search index for each user, which is constantly updated in real time.
And the third is a mailbox that behaves like an active database, containing state that can never be

archived, what labels does it belong to, what thread of the conversation does it belong to, or is it

open the message. The unread flag changes, and this is a write operation. Star a message and move it
to a label, archive it, or save it as a draft, and you generate even more leads. Now imagine doing
this on your laptop, phone, tablet, and web browser, all logged into the same account. The challenge
now is not to save those emails. The challenge is to ensure that every device sees the same reality
at the same time . So if you mark a message as read on your phone, your laptop won't be able to
continue to show it as unread. And if you save a draft on one device, it won't disappear on another.
And if you archive a conversation, that change should be reflected everywhere. Nowadays, users
rarely think about these requirements, but they immediately notice them when they don't work . At
this point, the mental model of a folder full of files completely breaks down because the files are
passive and the email is active. Each message is constantly queried , indexed, updated,
synchronized, and linked to other messages using labels and conversation threads. Gmail doesn't
actually manage a collection of documents , but a massive distributed automaton representing the
mailboxes of billions of users. And that's why email storage ultimately becomes a database problem,
because every message is a record, and every action is a transaction, and every device is
simultaneously reading and writing state . And unlike many apps, Gmail operates with two limitations
that are virtually non- negotiable. Firstly , it is durability. Losing someone's email is one of the
worst failures an email provider can have , and users may forgive a slow mailbox, but they won't
forgive data loss. Secondly, it is consistency. You can't let two devices disagree on whether a
message exists, whether it's been read, or what its state is. The entire experience depends on each
client adhering to the same truth. Now remember these two requirements: durability and consistency,
and almost every major architectural decision in Gmail stems from Google's refusal to compromise on
either of these two requirements. But hidden within this long list of email states is another design
decision that turns out to be no less important, and it is one that many engineers can directly
borrow from their own systems. Gmail's next major design decision looks like a UI feature , but it's
actually a database design choice. Traditional email systems organize messages into folders. A
folder is essentially a hierarchy. Each message belongs in exactly one place, so if you wanted the
same email to appear in multiple folders, the system had to either create copies or maintain complex
distinctions between them. Both approaches introduce additional complexity . Now took a different
path and introduced labels instead of folders. A tag is simply metadata added to a message. The same
email can be simultaneously marked as work, important, receipts, and travel, while still existing as
a separate record in the repository. This way, it will not have any duplication and will not have
any synchronization between copies. There will be only one message, and there will be many ways to
classify it. From a data modeling perspective, this is a significant shift, as the system moves from
a rigid tree structure to a flexible many-to-many relationship between messages and labels, and this
change has an interesting consequence. When you archive an email in Gmail, nothing is actually
moved. There is no archive folder waiting somewhere else on the system. The message remains exactly
where it was before. Gmail simply removes the inbox label . The same message still exists. It still
belongs to the same conversation thread. Still showing up in search results. It simply no longer
meets the condition required to appear in your inbox . In fact, your Inbox is n't really a folder at
all. This is just a request. For example, the query would look like this: Show for each message that
currently has the Inbox label. A custom label is actually a query, and every screen you see in Gmail
is just another question asked of the same basic collection of messages. And this is Gmail's "search
first" philosophy, expressed directly in the data model. Messages are stored once, metadata
describes them, and different representations arise by querying this metadata. This is a great
design because it separates storage from organization, and messages don't need to be moved around
the system to appear in different places. The system only needs to quickly answer questions about
them. And this last requirement turns out to be critical, because once every inbox label chain and
search result is generated by querying the same underlying data set, the performance and correctness
of those queries become central to the entire user experience. Which brings us to the two guarantees
that every large-scale email system should provide : durability and consistency. Durability means
one thing: once a message is received, it is never lost. Once Gmail notifies the sender that a
message has been delivered, that message has to survive whatever happens next. It could be a failed
drive, a machine catching fire, an entire data center losing power, and none of that is really
allowed to cause you to lose your email. On the scale of Gmail, this is not hypothetical. With
millions of disks in operation, some fail every hour of every day . So, a single copy of an email
residing on a single drive or even in a single building is not durable in any sense. And the
mechanism of longevity is replication. The idea of ​​replication is simple. Instead of storing an
email on a single machine, the system stores multiple copies on different machines, and if one
machine fails, the other copy still exists. At first glance, this sounds like a complete solution
that involves simply making enough copies and you're safe, but replication raises questions. When do
you consider the right to receive complete? Imagine an incoming email is delivered to one machine
and the system immediately responds successfully and starts creating additional copies after that in
the background. Technically, the design uses replication, but there is a dangerous gap. For a brief
moment, only one copy of an email exists, and if that machine fails before replicas are created, the
email effectively disappears, even if the sender has already been notified that it is safely stored.
What matters is whether these replicas exist before or after the system confirms the right to
receive. A strong system changes this order. An incoming email is not considered written until it
has been transmitted to multiple machines, ideally in different physical locations. Only then is its
receipt confirmed, and you pay for it with a slight delay as you wait for confirmation from several
places before agreeing. And then any single machine or an entire site can disappear without losing a
single byte, because other copies are still stored. And this single rule is the foundation of the
entire promise of no data loss. A right is never recognized until it is safely stored in several
places. But durability creates a new problem. The new problem is that the same email now exists in
multiple copies in multiple places, and you read your email simultaneously from your phone, laptop,
and browser. They all have to agree on the truth. So, you open a message on your phone, it's read,
and you turn on your laptop 2 seconds later, and it should already show that message as read. You
apply a label on your desktop and your phone should already reflect that. And two records arriving
at the same time cannot collide and leave the state jumbled. So this is a consistency problem, and
it's one of the really difficult problems in distributed systems. Copies of your data are on
separate machines that are coordinated over a network, and that network is slow and unreliable
compared to the speed at which you click. Many systems solve this by agreeing on a final version,
and they allow the copies to diverge briefly and promise that they will convert soon. For many apps,
this is actually a pretty reasonable deal, but for email, it's a bad deal, because imagine deleting
a message on your phone and watching it reappear on your laptop within 30 seconds. People expect a
mailbox to behave as a single entity, not as multiple copies that negotiate. So, Gmail requires
strong consistency or marking your inbox as read and watching the unread count flicker again. And
every device and every location always sees one consistent version of reality. And for a long time,
the conventional wisdom was that you couldn't have everything at once, like strong coherence, global
distribution, and massive scale all at the same time. You had to choose only two of them. And this
limitation is exactly what Google aimed to destroy. The system that broke it is called Spanner.
Google's own engineering articles confirm that Gmail runs on it, storing the exabytes of data we
described. Spanner is a globally distributed database that is also strictly consistent, supports
complete transactions, and provides real-time asset guarantees where a set of changes either occur
completely or none of them occur without half-finished states in between. And this combination is
the interesting part. Typically, these strict transactional guarantees come from only a single
machine database, which cannot scale. But at the moment of data distribution, you are expected to no
longer have transactional guarantees. But Spanner somehow keeps them. You can distribute data across
machines and continents, add capacity almost without limit, and still treat it as one coherent,
strictly consistent database, where transactions behave correctly , and every reader sees the same
truth. As for Gmail, it's close to ideal, because an inbox is a small package of states that should
never be lost and should never contradict itself, multiplied by over a billion users. The mapping is
clean and durable because Spanner replicates data in different locations and refuses to acknowledge
a claim until enough copies hold it . And it's consistent because Spanner provides a single global
order for all operations, and scalable because it was designed from the start to be distributed
across as many machines as needed, which leaves one question, and it's complicated. How do you
maintain a single, consistent order of events across machines that are thousands of miles apart and
can only communicate over a slow network? Now the answer comes from an unexpected place–from
watches. Now here's the main difficulty. To place all the world's operations in the same order, the
obvious approach is to timestamp each one and sort by time. But computer clocks cannot be trusted
with this . Each machine's clock is slightly off, and they diverge from each other by milliseconds,
and on a global scale, these small discrepancies are enough to change the order of events and
disrupt coherence. So, using only timestamps does not work in a distributed system . This is why
global strong coherence was considered impractical, but Google's answer was to stop treating clocks
as unreliable and instead turn time into a reliable service. They installed atomic clocks and GPS
receivers in each data center and created a service based on this equipment called TrueTime.
TrueTime does one unusual thing. Instead of claiming to know the exact current time, it is honest
about its own uncertainty and returns an interval. True time is somewhere between this value and
that value, and it keeps that interval very small, just a few milliseconds, relying on the precise
hardware down below. Now that your clock knows how wrong it can be, you can use that to ensure
order. When Spanner commits a transaction, it assigns a timestamp and then intentionally waits. It
pauses for the duration of the uncertainty interval before making the result visible. This pause is
called the fixation wait . The effect is accurate. By the time someone can observe a transaction,
its timestamp is guaranteed to be in the past everywhere on Earth. So, if one transaction completes
before another begins, the timestamps correctly reflect that order on each machine without a central
coordinator to arbitrate it. This is how the same mailbox, replicated in different countries,

Receiving email is where interesting problems arise. Whenever someone sends you a message, Gmail

The email must be written to be durable and reproducible, spam and security checks must be
